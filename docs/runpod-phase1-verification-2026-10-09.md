# RunPod Phase1: Open WebUIで小型Qwenの1回答を確認

2026年10月9日、Open WebUIからRunPodのHTTPS接続を通じて `Qwen/Qwen2.5-1.5B-Instruct` の回答を表示できた。GPU起動前の計測開始から、回答確認・Stop・最初の課金ゼロ表示の確認まで約5分20秒。今回の稼働費の概算は約 **$0.051** で、確定請求は反映待ちである。

これは独立した小型モデルの接続試験である。このリポジトリのQwen3.8-27B、画像生成・編集、Gradioアプリ全体や、別リポジトリの統合launcherの実機検証を完了したことは意味しない。Phase2は未実施。

## 試験構成

| 項目 | 確認した構成 |
| --- | --- |
| GPU | RTX PRO 4000、VRAM 24GB、1台 |
| モデル | Qwen/Qwen2.5-1.5B-Instruct |
| 推論コンテナ | vllm/vllm-openai:v0.31.0、CUDA 13系 |
| 実GPUドライバ | 580.167.08 |
| ディスク | 一時container disk 30GB、永続ボリュームなし |
| 画面 | Open WebUI |
| 通信 | Open WebUI → RunPod HTTPS proxy → 認証guard → loopback上のvLLM |
| 試験時の時間単価 | GPU $0.57/時 + container disk $0.004/時 = $0.574/時 |

vLLM v0.31.0の[公式Dockerfile](https://github.com/vllm-project/vllm/blob/v0.31.0/docker/Dockerfile)ではCUDAの既定が13.0.3。今回のイメージはタグで記録されており、実際に取得したイメージのdigestは記録されていない。

guardはルート判定より先に認証し、外向けの許可対象を `GET /v1/models` と `POST /v1/chat/completions` に限定した。vLLMは `127.0.0.1:8001` で待ち受け、公開側の8000番ポートにはguardを置いた。短い回答用に出力を最大64トークンに制限した。推論用の既存キーを使い、管理APIキーをWeb UIへ流用しなかった。

この記録が示すのは認証guardを介した回答の表示であり、未認証リクエストの拒否を含む全経路の実環境テストを完了したという主張ではない。

## 初期の失敗と最終結果

先行試験ではモデル準備完了まで進んだものの、Open WebUIでの回答は未確認だった。停止後に同じPodへGPUを再割り当てできず、接続確認を続けられなかった。

最終試験では画面を先に準備し、新Podの起動後に接続URLを更新した。保存済みの推論キーを維持し、API形式をChat Completionsに合わせた。最初のチャット要求は拒否されたため、チャットのFunction CallingをLegacy、`max_tokens` を64に合わせ、同じ短い質問で再試行した。拒否原因を実際の送信payloadで確定したわけではない。

質問は「日本語で『接続確認できました』と一文だけ返してください。」。画面には **`Connected successfully.`** と表示された。接続して生成結果を表示する目的は達成したが、日本語の指定には従っていない。回答品質や指示遵守、生成速度の評価には使わない。

## 時刻・費用・清掃

以下は2026年10月9日の日本時間（JST）。計測開始はGPUの課金開始時刻そのものではなく、起動操作の直前に置いた保守的な基準時刻である。

| 記録点 | 時刻 |
| --- | --- |
| 起動前の計測開始 | 19:31:51.726 |
| 回答表示を確認 | 19:37:03.531 |
| Stop操作開始 | 19:37:04.778 |
| Stop確定操作 | 19:37:08.023 |
| 最初の停止・$0/時の表示確認 | 19:37:11.504 |
| 新Pod削除後の確認 | 19:38:56.490 |

最初の停止確認まで319.778秒。試験時のGPU・ディスク単価をこの全時間に掛けると、`319.778 / 3600 × 0.574 ≈ $0.05099`、丸めて約$0.051となる。これは今回の最終試験だけの概算で、先行試験を含む総費用ではない。

別の停止画面を取得した時点まで長めに数えた記録では340.945秒・約$0.05436、単価を$0.58/時へ切り上げると約$0.05493。停止表示を確認した後の時間も含むため、これも実請求額ではない。請求画面には1時間の反映遅延があり、試験単位の確定請求は待機中だった。

回答確認後にStopし、個別承認を受けて今回の新Podを削除した。先行試験の旧Pod2台も削除済みで、最終確認時の支出速度は **$0.000/時**。これはその時点の課金速度であり、過去の使用料がゼロという意味ではない。旧Podの削除時刻はこの記録では確定していない。自動入金の設定は変更しなかった。

## Stopと再開から得た学び

RunPodではStopするとGPUの占有を解放する。同じPodを保持していても、元の物理ホストで他の利用者がGPUを使っていれば再開できない。再開時にGPUがない状態と、RunPod全体で同型GPUがない状態は区別する必要がある。[公式の再開時GPU不足の説明](https://docs.runpod.io/pods/troubleshooting/zero-gpus)

一時container diskはStopで消去され、停止中は課金されない。永続volume diskは異なる保存・課金条件を持つ。今回は永続領域を設けておらず、停止後のモデルキャッシュ保持を前提にしない。[公式の保存・料金仕様](https://docs.runpod.io/pods/pricing)

短い試験では、Web UIの準備を済ませてからGPUを起動し、接続URL更新、モデル準備、回答表示の確認までを同じ稼働区間で進める。成功・失敗・時間上限のいずれかでStopし、停止表示と課金速度を確認する。画面設定の引き継ぎのために途中Stopを挟むと、次のGPU割り当てを保証できない。
